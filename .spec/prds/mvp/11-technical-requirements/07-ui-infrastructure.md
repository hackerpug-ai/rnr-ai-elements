# UI Infrastructure

## Token strategy — declare nothing, consume everything

**Source of truth:** The CONSUMER's `global.css` — their Tailwind v4 `@theme` block under `@layer theme { :root { @variant light { … } @variant dark { … } } }`, resolved by Uniwind. This library declares ZERO tokens: it ships no `global.css`, no `@theme` block, no `--*` custom property, no `THEME`/`NAV_THEME` object, and no color literal (`#`, `rgb(`, `hsl(`, `oklch(`) in any component. Every color is a Tailwind utility naming a semantic role. The acceptance test for this rule is mechanical: swap the consumer's `@theme` for a different shadcn theme, rebuild, and every AI element must recolor with no library edit and no diff. A grep for `#[0-9a-fA-F]{3,8}` in `registry/**/*.tsx` returning any hit outside a documented foreign-surface bridge is a build failure.

Roles consumed: `background / foreground`, `card / card-foreground`, `popover / popover-foreground`, `primary / primary-foreground`, `secondary / secondary-foreground`, `muted / muted-foreground`, `accent / accent-foreground`, `destructive`, `border`, `input`, `ring`, `radius`, `chart-1..chart-5`

### New tokens needed

**NONE — the recommendation is zero new tokens, and this is a hard rule, not a preference**

- Why: The library is distributed as a copy-paste registry into an EXISTING RNR app. Any `@theme` entry we require is a manual edit to the consumer's `global.css` at install time. That edit is (a) invisible to the RNR CLI, which copies component files and registry dependencies but does not merge theme blocks; (b) silently broken when omitted — an unresolved `--color-reasoning` renders transparent or falls back, not an error; and (c) permanently un-synced when the consumer later swaps themes. Every new token is therefore a latent visual-parity bug with no failure signal. The promise 'little visible difference from the RNR system' is only enforceable if the color set is literally identical.
- Instead: Compose from existing roles with opacity modifiers, exactly as RNR does. RNR itself never adds a role to express a new state: it writes `bg-primary/20` (Progress track), `bg-muted/50`, `dark:bg-input/30`, `active:bg-primary/90`, `dark:bg-destructive/60`, `ring-ring/50`. Every AI Elements surface resolves the same way.

**REJECTED CANDIDATE: --color-reasoning / a 'thinking trace' surface**

- Why: Reasoning is visually a disclosure over a lower-emphasis body of text — a semantic weight, not a new hue.
- Instead: `bg-muted/50` container + `text-muted-foreground` body + `border-border`, disclosed by Collapsible wearing Accordion's trigger styling. Zero new tokens. The web original does exactly this.

**REJECTED CANDIDATE: --color-success / --color-warning for tool status**

- Why: AI Elements needs green (output-available), orange (output-denied), red (output-error). RNR has only `destructive`.
- Instead: Map error → `text-destructive` (a real RNR role). For success and denial use Tailwind v4's BUILT-IN palette — `text-green-600 dark:text-green-500`, `text-orange-600 dark:text-orange-500` — which requires no `@theme` entry because Tailwind ships the default palette. This is byte-for-byte what the web original does (`text-green-600`, `text-orange-600`, `text-red-600`). Parity is preserved by the strongest available argument: OUR DEVIATION SET EQUALS THE WEB ORIGINAL'S DEVIATION SET. Where AI Elements-on-web uses a shadcn token, we use the RNR token; where it departs from shadcn, we depart from RNR by the identical amount, in the identical place. Confine these three literals to one exported `statusColor` map so they are auditable in a single file.

**REJECTED CANDIDATE: --color-code-* / a syntax-highlight palette**

- Why: Syntax colors are a closed palette owned by a highlighter theme; they cannot be expressed as semantic roles.
- Instead: Treat the code-block INTERIOR as a foreign surface, which is what it already is on the web (shiki emits inline hex that is not a shadcn token). The block's CHROME — border, radius, header, copy button, background — stays 100% RNR (`bg-muted`, `border-border`, `rounded-md`). MVP interior is unhighlighted mono on `bg-muted`, matching RNR's own `Text variant="code"` recipe (`bg-muted rounded px-[0.3rem] py-[0.2rem] font-mono text-sm font-semibold`). Highlighting arrives later as an opt-in prop, and when it does its palette is a prop-supplied theme object, never an `@theme` entry.

**REAL GAP, not a color token: a native monospace font family**

- Why: RNR writes `font-mono` in `Text variant="code"`, but Tailwind's `font-mono` is a CSS font STACK. React Native needs a single resolvable family name. Whether Uniwind 1.11 resolves `font-mono` to a working native family is UNVERIFIED — I could not confirm it from source, and expo-ai-elements sidestepped it entirely with a hand-rolled `MONO_STYLE` in `lib/fonts.ts`. code-block, terminal, stack-trace, snippet, schema-display, and tool-input all depend on it.
- Instead: Do NOT add a font token. Ship ONE shared `lib/mono.ts` exporting `Platform.select({ ios: 'Menlo', android: 'monospace', default: 'monospace' })`, used by every mono surface — and delete it the moment a device test proves `font-mono` resolves. Whichever way it lands, it MUST be one file: six components each choosing their own family is guaranteed drift.

## Density reconciliation

**Touch-target rule:** Keep RNR's VISUAL box; grow only the INVISIBLE hit area. RNR's mobile default control is `h-10` (40pt) and its icon button is `h-10 w-10` — both 4pt under Apple's 44pt HIG and Android's 48dp guidance. The resolution is `hitSlop={{ top: 2, bottom: 2, left: 2, right: 2 }}`, which yields a 44x44 effective target with a zero-pixel visual delta. This passes through RNR's Button unchanged, because Button spreads `...props` straight onto Pressable — verified in its source. Three corollaries, all hard rules: (1) NEVER author `h-11`/`h-12` to reach 44pt — an AI Elements button taller than the host app's buttons is the exact 'that's the chat library' tell; (2) adjacent interactive elements need >=8pt of separation so expanded hit areas do not overlap and steal each other's taps; (3) hitSlop is the ONLY sanctioned deviation from RNR's box model, and it is sanctioned precisely because it is invisible.

Where density gives:

- ACTION TOOLBARS (toolbar, message actions, prompt-input controls). Web shows 5–6 ghost icon buttons; at RNR's 40pt that is 200–240pt of width on a ~390pt screen. Show at most 3 inline, overflow the rest into a DropdownMenu behind a `MoreHorizontal` icon button — or a long-press ContextMenu on the message itself. Both are RNR components, so the resulting screen still reads as RNR.
- TABULAR AND CODE CONTENT (code-block, test-results, schema-display, terminal, stack-trace). Never shrink to fit: scroll horizontally inside a ScrollView. `text-xs` (12) is the floor and it is already in use for the web's section labels, so there is no room below it. Shrinking would break the type ramp AND the accessibility size floor in one move.
- MULTI-PANE LAYOUTS (panel, canvas + inspector, sandbox, sidebar-shaped surfaces). Two side-by-side panes become RNR Tabs, or a primary pane plus a modal detail. Prefer Tabs — it is RNR vocabulary and costs nothing in parity.
- TREE INDENTATION (file-tree, schema-display). Cap the per-level indent at ~16pt and scroll horizontally past ~4 levels. Web's ~24pt/level exhausts a phone's width by depth 5.
- LONG PAYLOADS (tool inputs/outputs, JSON blobs, reasoning traces). Collapse to N lines with a 'Show more' `Button variant="link" size="sm"`. AI Elements already collapses tool content behind a disclosure; extend the same idea one level deeper.
- DISCLOSURE DEFAULTS. On the web, Tool and Reasoning can afford to sit open. On a phone, default everything except the actively streaming reasoning trace to collapsed, so the transcript stays scannable.
- SPACING — AND THIS IS THE ONE THAT GOES THE OTHER WAY. RNR's mobile density is LOOSER than AI Elements' desktop density (`px-6`/`py-6`/`gap-6` cards vs the web's `p-3`/`p-4`). Where the two disagree, take RNR's. We are not compressing a desktop layout onto a phone; we are authoring at the host app's existing mobile rhythm.

**Parity cost:** NEAR ZERO for the touch-target rule — hitSlop changes no pixel, so a screenshot diff against an RNR screen is clean. LOW for overflow menus, horizontal scroll, and collapse-by-default: each is assembled from DropdownMenu, ContextMenu, ScrollView, and Button, all already present in the host app, so the added elements read as RNR rather than as ours. HIGH, and unavoidable, for multi-pane collapse: turning two panes into Tabs is a structural change no styling can hide. It is nonetheless the CHEAPEST high-cost option, because Tabs is RNR's own component — the alternative, a hand-built resizable or bottom sheet, would invent a drag handle, a backdrop opacity, a spring curve, and a radius with no RNR reference to match, and would therefore break parity harder than the layout change it was meant to avoid. Net: density gives in the places where RNR itself already has an answer, and the promise survives.

## Accessibility

- **Contrast floor:** WCAG 2.2 AA: 4.5:1 for body text, 3:1 for large text (>=18pt regular or 14pt bold) and for icons and control boundaries that carry meaning. The floor is inherited, not re-derived — RNR's default oklch palette already clears it for foreground/background and muted-foreground/background, so any pair we compose is the only new burden. Two pairs must be measured rather than assumed: (1) `text-muted-foreground` on `bg-muted/50`, used for tool parameter panels and reasoning bodies — this is foreground-on-tinted-surface and is the most likely failure in the whole library; and (2) the status colors `green-600`/`orange-600` on `bg-secondary` badge fills in BOTH schemes, since they answer to no theme and were chosen by the web original for a white desktop background. Because status is also carried by a distinct icon (CheckCircle / XCircle / Clock / Circle) and a text label, color is never the sole channel — which satisfies WCAG 1.4.1 independently of the ratio and is the reason the green is tolerable at all.
- **Reduced motion:** RNR's convention is `.reduceMotion(ReduceMotion.System)` chained onto every Reanimated entering/exiting animation — verified in Tooltip and mandated across the registry. Every overlay and disclosure we ship follows it verbatim, which makes disclosure motion compliant for free. BUT RNR's own Skeleton does NOT honor it: its `withRepeat(withTiming(0.5, {duration:1000}), -1, true)` loop runs regardless. Looping animations therefore get no free pass, and this library has several — shimmer, the tool `input-available` pulse, the speech-input level meter, and any streaming indicator. Rule: every LOOPING animation is gated on `useReducedMotion()` from react-native-reanimated and falls back to a static resting state (shimmer becomes plain `text-muted-foreground`; the pulsing clock icon becomes a still clock icon). This is one place we are stricter than RNR, which is acceptable because it changes nothing visually when reduced motion is OFF — the parity promise is untouched. A continuously looping animation is also a WCAG 2.2.2 concern (>5s of moving content needs a pause mechanism), and streaming responses routinely exceed five seconds.
- **Screen reader + streaming:** The hardest problem in the library, and the one most likely to ship broken because it is invisible in a screenshot. A `<Text>` whose content mutates 10–20 times per second makes VoiceOver and TalkBack restart their utterance on every change — the user hears the first three words, forever. Even the 80ms throttle still yields ~12 mutations/second. The contract: (1) WHILE STREAMING, the mutating text is hidden from the accessibility tree (`accessibilityElementsHidden` on iOS, `importantForAccessibility="no-hide-descendants"` on Android) and a single STABLE sibling node exposes `accessibilityLabel="Assistant is responding"`; (2) ON STREAM END, the hidden state lifts, the full text becomes one readable node, and exactly ONE `AccessibilityInfo.announceForAccessibility()` fires with the completed message — a single announcement, not a live region. (3) `accessibilityLiveRegion="polite"` is used ONLY on nodes that change at human pace — the tool status badge transitioning input-streaming to output-available is a legitimate live region; the streaming text body is not. (4) The reasoning duration counter must NEVER be a live region — a per-second tick would chatter continuously; announce once on completion as 'Thought for 8 seconds'. (5) Every icon-only control carries `accessibilityLabel` and `accessibilityRole` (RNR's Button already sets `role="button"`; Text's h1–h4 variants already emit `role="heading"` + `aria-level`, which is why headings must go through the variant rather than a hand-written size class). (6) Disclosure triggers expose `accessibilityState={{ expanded }}`. NONE of this is provable from source review — it requires a device pass with VoiceOver and TalkBack against a real token stream, not the simulated setTimeout demo.
- **Dark mode:** Entirely the consumer's, with zero wiring from us. Their `global.css` carries `@layer theme { :root { @variant light { … } @variant dark { … } } }`; Uniwind resolves the active variant; `useColorScheme()` selects the app scheme. Because this library declares no token and no color literal, dark mode works the instant it is installed and keeps working when the consumer swaps themes. The acceptance test is mechanical: swap the consumer's `@theme` block for a different shadcn theme, rebuild, screenshot both schemes — every AI element must recolor with no library edit. RNR's own dark-mode idioms are inherited too (`dark:bg-input/30` field fills, `dark:bg-destructive/60`, `dark:active:bg-accent/50`, Skeleton's `bg-secondary dark:bg-muted`), which is what makes our surfaces match the host app in dark mode rather than merely being dark. THE ONE EXCEPTION, and it is the highest-severity theming risk in the project: renderers that consume STYLE OBJECTS rather than classes — the markdown renderer, and any future syntax highlighter — cannot read Tailwind classes at all. They need theme VALUES in JavaScript. Those values must be read from the consumer's resolved theme at runtime, never hardcoded. expo-ai-elements hardcoded a `DARK_MARKDOWN_STYLE` hex constant and shipped no light-mode object at all, which is exactly why re-theming markdown there is a manual edit to a copied file — the failure this library exists to avoid. Note also that `NAV_THEME`/`lib/theme.ts` is the CONSUMER's concern (native header and tab-bar chrome); we neither ship nor require it, but any documented example screen must mention it, because a correctly themed body above a stale native header is the classic RNR half-done theme.

## Hard UI constraints

- ZERO tokens declared. No `@theme` block, no `--*` property, no `global.css`, no THEME/NAV_THEME object ships from this library. CI gate: grep `registry/**/*.tsx` for `#[0-9a-fA-F]{3,8}`, `rgb(`, `hsl(`, `oklch(` — any hit outside a documented foreign-surface bridge fails the build.
- Uniwind + Tailwind v4 ONLY. No `tailwind.config.js`, no `hsl(var(--token))`, no `.dark:root`, no `inlineRem`, no `hairlineWidth()`, no `tailwindcss-animate`. Those are Nativewind-path constructs and are inert or wrong here. The RNR KB's theming.md documents the Nativewind path; MIGRATION.md v1.1.0 is the correction that governs.
- No bare strings. Every label is inside `<Text>`. This is the single most common LLM-generated RNR bug and it is a hard render error, not a style issue.
- No cascade. A parent's `className` never reaches a descendant `Text`. Any component intending to influence descendant text publishes via `TextClassContext.Provider` — as Card, Button, Badge, Accordion, and Tooltip all do.
- Class order is always `cn(variants, contextClass, className)` so a consumer's `className` wins. Non-negotiable: it is the override path the theming promise depends on.
- Web-only utilities live exclusively inside `Platform.select({ web })`: `hover:`, `focus-visible:`, `transition-*`, `outline-none`, `cursor-*`, `whitespace-nowrap`, `select-*`, `data-[…]:`, `[&>svg]:`, `has-[>svg]:`. Every `hover:` needs a base `active:` twin.
- Native state styling is prop/state-driven Reanimated, never `data-[state=open]:`. Extract ONE chevron-rotation hook (250ms open / 200ms close) — the pattern recurs in at least six of the 49 elements, well past the Rule of 2.
- Icons only via `<Icon as={X} />`. A raw Lucide element silently ignores className under `withUniwind`.
- Every portalled surface needs `<PortalHost />` at the consumer's root — documented as an install prerequisite — and every ANCHORED surface (Select, DropdownMenu, ContextMenu, Menubar, HoverCard) needs `insets={contentInsets}` derived from `useSafeAreaInsets()` with the registry's Android `bottom + 24`. Missing either fails silently: no error, nothing on screen, and it reproduces only on hardware.
- Overlays keep the `FullWindowOverlay` iOS guard and animate through `NativeOnlyAnimatedView` with `.reduceMotion(ReduceMotion.System)`.
- Menu-family close is `TriggerRef.close()`, never `setOpen(false)`.
- Motion durations come from the fixed set {150 overlay-in, 200 layout/exit, 250 chevron-open, 1000 pulse}. New durations require an explicit decision.
- hitSlop is the only sanctioned deviation from RNR's box model, precisely because it is invisible.
- `text-xs` (12) is the type floor. Content that does not fit scrolls; it never shrinks.
- One shared mono-font module, one shared status-color map, one shared chevron hook, one shared code-block shell (consumed by code-block, terminal, stack-trace, snippet, tool-input, schema-display), one shared tree renderer (file-tree + schema-display). Each of these appears well past the Rule of 2; duplicating any of them guarantees drift.
- Foreign-surface bridge: markdown style objects and any future syntax theme MUST derive their values from the consumer's resolved theme at runtime, never from hardcoded hex. expo-ai-elements' hardcoded `DARK_MARKDOWN_STYLE` is the anti-pattern — it is why re-theming markdown there is a manual edit to a copied file.
- New runtime dependencies (webview, svg, av, masked-view) are per-element and must be declared in that element's registry item only, so a consumer installing `message` does not pull a WebView.
